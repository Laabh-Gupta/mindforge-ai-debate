# Deploy: Netlify Free + Render Free + existing Supabase

## Before you start: install from the repository root

Run these commands in Git Bash, including when your terminal is currently inside frontend/:

```sh
cd /d/Projects/mindforge-ai-debate
bun install --frozen-lockfile
```

This repository uses one root package.json and bun.lock for both applications. The frontend/ and backend/ directories contain their separate source code. Keep Bun as the package manager for reproducible installs and deployment builds.

Supabase's generic JavaScript/Next.js quickstart is a different integration. This app uses the backend's existing pg driver to connect to Supabase PostgreSQL and Better Auth for sign-in. You do not need to run `npm install @supabase/supabase-js @supabase/ssr`, create a Supabase browser client, or configure NEXT_PUBLIC_SUPABASE variables. The frontend is a static Vite app.

Copy the templates only when the destination does not already exist, so existing credentials are preserved:

```sh
[ -f backend/.env ] || cp backend/.env.example backend/.env
[ -f frontend/.env ] || cp frontend/.env.example frontend/.env
```

Keep actual secrets in backend/.env. The committed .env.example files contain empty credential fields and public example settings only.

## 1. Connect the existing Supabase database

Open the existing Supabase project, select **Connect**, and copy the **Session pooler** PostgreSQL URI (port 5432). This supports IPv4 connections from a persistent backend. Replace only the password placeholder with your database password, URL-encoding special characters. The Supabase anon/publishable API key is not a PostgreSQL password.

Set DATABASE_URL in backend/.env locally and in Render's secret environment settings. Use SSL certificate verification, for example the connection URI with sslmode=verify-full. If your project requires a CA, configure its downloaded certificate with NODE_EXTRA_CA_CERTS on the server. Do not disable TLS verification.

Keep the new **mindforge** schema out of Supabase's Data API exposed schemas. The backend initializes its application tables and Better Auth tables there on startup. It does not change existing public tables, Supabase Auth users, or historical migrations. The SQL connection role must be able to create and use this schema. All user access goes through server ownership checks; no database keys are sent to the browser.

Existing Supabase Auth users are not automatically Better Auth users. Existing local SQLite accounts also need an explicit migration before they can sign in against PostgreSQL; keep your old data directory and AUTH_SECRET backed up. To import the old local database, stop the backend, keep the original AUTH_SECRET in backend/.env, and point DATABASE_URL at the empty target schema. Back up the local file, then run:

```sh
bun run db:import:sqlite data/mindforge.sqlite
```

The command opens SQLite read-only, imports all accounts, password hashes, sessions and practice records in one PostgreSQL transaction, and refuses a nonempty target. Do this before accepting new signups on the deployment. Do not delete the source backup until login and history have been verified. Supabase Auth accounts require a separate explicit migration and are never overwritten.

No existing records are deleted by setup. Guest history remains in the same browser localStorage keys.

Official connection guidance: https://supabase.com/docs/guides/database/connecting-to-postgres
Schema isolation: https://supabase.com/docs/guides/api/securing-your-api

## 2. Create the frontend site and backend service

1. In Netlify, import this repository from **main**. Use repository root as base, build command **bun run build:frontend**, publish directory **frontend/dist**. Reserve the final site name; note its HTTPS origin.
2. In Render, create a Blueprint from this repository. render.yaml selects **Free**, Docker, main, backend/Dockerfile, and /api/health.
3. Set Render DATABASE_URL, FRONTEND_ORIGIN to the exact Netlify origin (no trailing slash), and GROQ_API_KEY. AUTH_SECRET and SESSION_SECRET are generated by the Blueprint. Preserve AUTH_SECRET if migrating encrypted existing account data. Neither secret should change on redeploy.
4. Note the Render HTTPS origin. Add **VITE_BACKEND_ORIGIN** to Netlify's build environment with that exact origin, then redeploy Netlify.
5. Add Google and email credentials below on Render, then redeploy the backend. No credentials belong on Netlify.

The Netlify build generates /api proxy rules before the SPA fallback. Auth and practice history use this same-origin proxy so HttpOnly cookies work on netlify.app without third-party cookies. Google callbacks also use the Netlify origin.

AI streaming and longer reviews connect directly to Render with an expiring, signed AI-only capability in memory. CORS permits only FRONTEND_ORIGIN. These tokens cannot access account records. This avoids Netlify's 26-second proxy timeout. A direct health request wakes Render before account requests; the UI explains the wait. No keep-alive automation is used.

## 3. Email/password and Google sign-in

Email/password sign-up and sign-in work without Supabase Auth or a mail service. Password recovery requires HTTPS email delivery:

- Create a Resend API key and verify a sender domain.
- Set RESEND_API_KEY and MAIL_FROM on Render.
- Render Free blocks SMTP ports, so this app uses the Resend HTTPS API.
- Without these values, recovery clearly reports that it is unavailable.

For Google, create a Web OAuth client in Google Cloud Console. Configure the consent screen and permitted test users while in testing. Add the authorized JavaScript origin matching Netlify and this exact redirect:

```text
https://YOUR-SITE.netlify.app/api/auth/callback/google
```

Set GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET on Render. For local development, register http://127.0.0.1:3001/api/auth/callback/google separately. Account linking requires a signed-in user; accounts are not silently linked by matching an email.

## 4. Free-tier expectations and launch checks

Render Free can sleep after 15 minutes of inactivity and take roughly a minute to wake. Supabase Free can pause inactive projects and has storage/usage quotas. Netlify Free has usage caps. This setup is suitable for a demo or small launch with those limits; it cannot promise always-on availability. Review each provider's current dashboard quotas. All persistent app data and rate counters live in Supabase, so Render restarts do not erase them.

After configuring credentials, verify email registration, three consecutive sign-ins, Google callback, password recovery, logout, guest practice, streamed replies, a review, cross-device history, and history deletion. Redeploy Render and confirm account history persists. Deep-link directly to /dashboard and /debate on Netlify. Confirm browser requests expose no database or Groq secrets.

Google token exchange, delivery to a real mailbox, a real Supabase connection and public deployment require your configured service accounts; local test success does not verify those external credentials.
